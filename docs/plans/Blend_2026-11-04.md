# Blend: the tool

Blend is a preprocessor of static objects for Bend (`README.md`):
`.blend` files in, `.bend` files out, the objects gone. It grew in
glam-in-bend as the vehicle for glam's kernel, its families written once
where Bend's templates thread hooks through every signature (that
repository's `codegen-vehicle.blend`; its plan `Blend_2026-11-04.md`
moves the kernel onto Blend). This plan builds the tool, its laws, and
what lies beyond. Reviewed by the maintainer, 2026-11-04: looks good, its
open questions answered (below). The samples may change to fit the
implementation, keeping their intention (the maintainer, 2026-11-04).
Paths are Blend's, from its root (`blend-own-repository`), but where
they name glam-in-bend's (`spike/`; `scripts/` before the split).

## Steps

### The tool

Written in Bend (`generated-sources`), in `blend.bend`, run as
`bend blend.bend COMMAND IN.blend` (a command word: Bend takes
arguments that begin with `-` as its own), the emitted file on its
output, as `spike/tools/gen_krules.bend` writes `spike/krules.bend`.
Built natively once for each version of its sources and of Bend
(`build.sh`, into `results/build/`; 13 s and 0.4 GB) and run as
`run.sh COMMAND IN.blend`: a run then takes milliseconds, where
`bend blend.bend` checks and compiles the tool each time (1.3 s;
2026-11-04, the maintainer: no need to recheck and rebuild it on every
run). `check.sh` takes 3.7 s with the tool built, 20 s before. Each step ends
with more of the samples passing, the tool's output compared with each
sample's `.bend`, or its error with the `.err`.

1. `blend-read` — built 2026-11-04 — a `.blend` file to a module: its
   bytes read as `spike/load.bend` reads a nets file; lines and
   indentation; the structure line by line (imports, objects and their
   parents, `declare`, members' headers with their sharing, `def` or
   `upd`, name, parameters and result, nested objects, the module's own
   definitions); each body kept as Bend tokens with their lines: names
   with dots, `_`, `^`, `~` before them, numbers with their suffixes,
   strings and chars, comments, the rest as it is. Done when every sample
   reads and its structure prints back.
   - `bend blend.bend read FILE.blend` prints the tree, an item a line
     with its line number, and under each definition the names its body
     holds. A line it cannot read (a header without a name or its
     parenthesis, an object's without `with`, a declaration of no name)
     is kept and printed with `?`, for `blend-objects` to report: reading
     never fails, and a malformed file, an empty one, a CRLF one, tabs,
     bytes past ASCII read without a crash. `check.sh` reads every
     sample, valid and invalid, and fails on a `?` line (the gate, about
     12 s more).
   - Bend has no mutual recursion: each loop that would call a helper
     calling back is one loop over a state record, its step deciding each
     turn, on fuel (the line count, the byte count).
   - Left for later steps: the reader is lenient where Bend will judge
     (a header's stray parenthesis, an object name with a dot, an import
     inside an object); bytes past ASCII print as Latin-1, so
     `blend-emit` writes bytes, not a String.
2. `blend-objects` — built 2026-11-04 — the objects: paths for nested
   objects, parents resolved, C3 as glam linearizes, the definitions each
   concrete object has, `def` and `upd` checked against what it
   inherits, `declare` against what a concrete object defines. Done when
   the samples `upd-undefined`, `def-defined`, `undeclared` and `no-c3`
   fail as their `.err` says, and the rest pass this far.
   - `bend blend.bend objects FILE.blend` prints each object's
     linearization and its definitions, each with the objects that gave
     it, the final first (`BoldLoud`'s `tag`: Bold < Loud < Plain); or
     the errors, `FILE:LINE: message` in line order. `check.sh`
     runs it on every sample: the four print their `.err` exactly, the
     rest no error.
   - A parent's name is found from the object's host outward to the
     module, dotted names by their parts (`Outer.In`); a parent named
     twice is one parent.
   - Errors besides the samples': a parent naming no object, an object
     inheriting from itself, an object defined twice in one scope, a name
     given twice in one object, two parents each introducing a name, an
     import inside an object, a line Blend cannot read; at the top level,
     `upd`, `declare` and sharing marks, the module being no object
     (`blend-module-is-bend`, revised 2026-11-04). Each is reported once:
     an error an object inherits from a parent is the parent's report.
   - Decisions on computed values go through `when`, its arms thunks, as
     Base does: a loop's next turn sits in an arm, inside the loop.
3. `blend-resolve` — built 2026-11-04 — the references in bodies: a
   name called, or passed with `~`, bound to the final definition of the
   innermost object that has it, the longest name defined; `_name` the
   prior, `^name` the host, `Obj.name` that object's; a parameter named
   as a definition an error, then a body's own binders. Done for `shadow`
   and `host-at-module`.
   - `bend blend.bend resolve FILE.blend` makes each concrete object's
     copies, the module's first: its finals, then each prior they reach
     (`BoldLoud.tag` reaches `BoldLoud.tag.Loud`, which reaches
     `BoldLoud.tag.Plain`), and prints what each copy's names reach, by
     the names `blend-emit` will give them. Every valid sample's
     references match its hand-written `.bend`.
   - A bare name is the concrete object's definition, then each host's
     of the object that wrote the body, innermost first, then one of the
     module's definitions, Bend's, its text kept; `^name` the host's
     scope, the module's at the top (`blend-module-is-bend`); a dotted
     name an
     object's definition, the longest object path first, objects found
     from the writer outward; otherwise Bend's.
   - A body's binders are found by line: `case` patterns, lets
     (`x = v`, `(a, b) = v`, `K{x, y} = v`, `a b = ...`), binds and
     annotated lets (`x : A <- m`), lambdas (`x =>`). Their scope is the
     whole body: a local is never named as a definition, so the
     approximation changes no binding, only which collisions it
     reports.
   - Errors besides the samples': a reference to an abstract object's
     definition, a `_name` with no prior, a `^name` its host lacks, a
     local named as a definition. A body copied into several objects
     reports an error once.
   - Stages: each command runs the stages before it and stops at the
     first with errors (read, objects, references).
4. `blend-emit` — built 2026-11-04 — the emitted module: names (`Obj.f`, the
   priors reached `Obj.f.Origin`, copies `Obj.f.c1`), the uses of each,
   the affine check, copies with the affine definitions they alone reach,
   callees first in source order among the unrelated, mutual recursion an
   error, Bend's imports and the module's own definitions as they are;
   what is emitted, every concrete object's definitions or those
   reachable from roots named on the command line, the command line's to
   say (the maintainer, 2026-11-04; revised the same day: every
   definition, so that a module several import is emitted once). Done
   when every valid sample's
   emission matches its `.bend` and `affine-twice` and `cycle` fail as
   they say; `check.sh` then runs the tool on every sample.
   - `run.sh emit FILE.blend`: every valid sample's
     emission is its hand-written `.bend` byte for byte, and every
     invalid sample fails with its `.err` exactly; `check.sh`
     holds them to it. Errors go to stderr with the status 1.
   - Order, the tool's choice beyond callees first (the maintainer,
     2026-11-04: Blend leaves it open, as it changes nothing Bend
     observes; so too the copies' numbers): the units in source order
     (the module's definitions and its concrete objects by their lines,
     an object's members in its linearization's order, its own first),
     each emitted after its callees, a walk from each in turn following
     calls in body order. A cycle is an error naming every unit on it.
   - Every definition emitted (the maintainer, 2026-11-04): the roots
     the command line named at first are gone, so that a module several
     import is emitted once, whoever imports it.
   - Sharing, over the emitted units, callers first: a copied unit gets a
     copy for each use, its users' copies counted, numbered in the order
     the uses are emitted; an affine unit used once by a multiplied unit
     goes with each of its copies, numbered alike (`Obj.h.c2` called from
     `Obj.g.c2`); an affine unit with two uses is an error naming each
     user and line; a copied unit no unit uses is emitted once by its
     own name. A prior takes its member's sharing.
   - Text: body lines re-indented by the definition's indentation,
     `upd` and the sharing marks gone, tokens as written; the bytes
     decoded as UTF-8 for printing, so text past ASCII passes through.
   - Revised 2026-11-04 (the maintainer): a copied unit is always
     emitted by its own name too, never conditionally
     (`blend-copies-keep-their-name`); the module is no object, its
     definitions Bend's (`blend-module-is-bend`), emitted as written and
     calling a copied unit by its own name. A copied unit used once still
     has its numbered copy, `.c1`, beside the one by its own name.
5. `blend-markers` — built 2026-11-04 — a line before each emitted
   definition naming its source (`# blend: knet.blend:120`), so that
   Bend's errors on emitted code lead back; the samples' `.bend` taken
   up to match.
   - A marker before each definition and none within: a body's lines are
     emitted as they are written, blank ones included, so the line k
     lines below a marker is the source's k lines below the one it
     names. `where.sh FILE.bend LINE` maps a line Bend reports to
     the `.blend` (a type error planted in a sample's body: Bend's line
     15, the source's 12).
6. `blend-generated` — built 2026-11-04 — emitted files checked current
   by `scripts/check_generated.sh`, its lines given the generator's
   arguments (`spike knet.bend ../blend/blend.bend knet.blend`), the
   pre-commit hook with it.
   - A line gives its generator's kind and arguments: `bend` a Bend
     program, `blend` Blend's emission of a `.blend` file, run built
     (`run.sh emit`; the build, 13 s, once for each version of
     Blend's sources). The samples' `.bend` files are generated files
     now, listed there; `check.sh` runs them and the invalid
     samples. The pre-commit hook takes 3.9 s with Blend built.
   - The build's key covers Bend itself, not its version alone (its
     version, its executable's size, time and inode, its Base and
     effects), so that an update of Bend in place rebuilds the tool
     (the maintainer, 2026-11-04: Blend's checks must survive Bend's
     updates); a stand-in reporting another version rebuilt it.

### Blend matures

The maintainer, 2026-11-04: Blend is drawing interest beyond this
project, so it matures before the kernel moves onto it: types in
objects, imports, nested objects extended, laws and proofs in objects,
and laws of Blend's own. Each feature's samples first, as before.

7. `blend-syntax` — built 2026-11-04 — small things: `with` may be left
   out of a header with no members after it (`object BoldLoud extends
   Bold, Loud`), members after such a header an error (the sample
   `missing-with`); the sample `static` renamed `choice`, apart from the
   `static` expressions `blend-partial` may bring; two emitted
   definitions of one name an error (a prior `Bold.tag.Plain` beside a
   definition `tag.Plain`, a copy `f.c1` beside `f.c1`, a module's
   `Bold.g` beside an object's), found while brainstorming laws.
   - `upd def f(...)` updates a definition, as `upd type` a type; `upd
     f(...)` alone is sugar for it (the maintainer, 2026-11-04); the
     sample `prior` gives both.
8. `blend-types` — built 2026-11-04 — types in objects, so that no family threads
   type parameters through its signatures (the maintainer, 2026-11-04,
   after Haskell's type families, Rust's traits with associated types,
   OCaml's module types):
   - A type member: `type S = P.Stk`, introduced and updated as a
     definition is (`upd type S = ...`), declared in an abstract object
     (`declare type S`) for each concrete one to give; its kind stated
     where it must be reusable (`type S: Data = List<&2, U32>`), `Type`
     otherwise.
   - A type constructor: `type Pair(A: Data) = A & A`, named
     `Pair(U32)`.
   - Emitted as a definition returning its type, `def Fam.S() -> Type:`,
     each name of it bound as a definition's is (`S` to `Fam.S()`):
     Bend takes a type a definition computes in a signature, through a
     match and inside a datatype's arguments, and erases it, the native
     build keeping no trace of it (tried 2026-11-04).
   - A definition's header bound as its body is: its parameters' and
     result's types name the type members (today only bodies are bound).
   - Abstract methods over an abstract type, constructors and observers:
     declared definitions whose signatures name it, each concrete
     object's copies checked by Bend against its own type.
   - Later, perhaps: a datatype in an object, its own for each concrete
     object (OCaml's functors make such types); a datatype of the
     module's with a type member as its argument (`Ev<S>`) covers what
     the kernel needs.
   - Samples first: a family whose state is a stack in one object and
     nothing in another; invalid, a declared type left undefined.
   - Built: the syntax is sugar (the maintainer, 2026-11-04): `type S =
     T` is `shared def S() -> Type: T`, its body on its header's line,
     emitted there (`def Sum.S() -> Data: U32`), so that markers stay
     exact; `upd type` and `declare type` are `upd` and `declare`; a
     type member is shared, as a type is erased. A name of one is a
     call, `S()`: no sugar at uses. Headers are bound as bodies are
     (`def Sum.add(+st: Sum.S(), ...) -> Sum.S():`), their uses counted.
     A datatype of the module's, Bend's, passes through after the
     imports, with its marker; one in an object is an error, its
     objects' own datatypes later. The samples `types`,
     `undeclared-type`, `object-datatype`; a type constructor updated
     down a linearization (`Pair(T())`, T updated to Nat) checked by
     Bend.
9. `blend-imports` — built 2026-11-04 — `.blend` files importing `.blend` files
   (the maintainer, 2026-11-04: the reason the module is no object, so
   that an object means the same however it is reached through the DAG
   of imports):
   - `import ./other.blend as M`: M's objects named `M.Obj`, extended
     (`extends M.Obj`) and called (`M.Obj.f`); an object is identified
     by its module's path and its own, so that a diamond of imports
     reaches one object; a cycle of imports an error.
   - Each module emits its own `.bend`, `other.blend` to `other.bend`,
     this one importing it as Bend's (`import ./other.bend as M`); an
     object extending `M.Obj` emits its own copies of what it inherits,
     and calls M's emitted definitions by their own names, so that
     sharing and copies are counted within each emitted module.
   - Several files on one command line, each emitting its own
     (`run.sh emit a.blend b.blend`), one root doing a dozen jobs
     by its imports (the maintainer leans to it, 2026-11-04). Built
     2026-11-04, once every definition was emitted and no top-level
     object could be extended, so that a module's emission depends on
     nothing importing it (the maintainer): `emit FILE.blend... [DIR]`
     writes each module named, its imports read and checked, not
     written, all of the command's files or none; DIR takes them flat,
     two modules writing one name an error. Revised 2026-11-05: an
     import never written by a command that does not name it, as a
     package's could not be (the maintainer); verified instead, emitted
     again in memory and compared with its files, a file stale, missing
     or no longer emitted an error, `--alone` the bypass
     (`blend-emit-verifies-imports`). A root named by its absolute path
     lost its `/` in its imports' paths, fixed, with a regression in
     check.sh.
   - Built: the command line reads the DAG from the root, breadth
     first, each file once by its path made plain (`.` and `..`
     resolved); a file an import names that none can read an error at
     the import. Each module's lines are numbered from its place times a
     million, the root's 0, so that a line's number names its file and
     every error and marker names the right one (`lib/shapes.blend:11`)
     with no file threaded through them. A module's root is the object
     that is its own host; `^` and scopes stop there; a dotted name
     whose first part is an alias is found in the module imported. Every
     module is checked (its objects, C3, definitions); the root alone is
     emitted. A reference into another module is emitted through the
     alias the root gives it, or the one another importer gives it,
     carried; the bodies copied from a module carry its imports, added
     where the root lacks the alias, an alias for two files an error at
     the carried import's line. Revised the same day
     (`blend-namespaces-as-bends`): what the copies need goes under
     aliases Blend reserves (`Blend_1`), never the other modules' own, so
     that the root's namespace is no larger for what it inherits; a
     copied body's datatypes and constructors (`S.Dim{...}`) and its
     module's aliases bound like its definitions. The samples `imports` (with
     `lib/shapes.blend`), `import-cycle`, `import-missing`; a diamond of
     four modules, one object reached by two aliases, C3 over it and
     priors across three files, run by Bend.
10. `blend-nested` — built 2026-11-04 — nested objects inherited and extended
    (the maintainer, 2026-11-04), as glam's are: an object has its
    parents' nested objects; `extend Inner with ...` in a child updates
    an inherited nested object as `upd` does a definition, `object
    Inner` there an error when one is inherited, as `def` is;
    `Outer2.Inner`, its own copy, linearized from the extensions down
    Outer2's linearization; `^name` in Inner's bodies bound to the final
    host's (Outer2's). Sample first.
    - Design, from glam's text (docs/Syntax.md, "Object Namespaces" and
      `extend`), for review before it is built: `^` steps out of the
      innermost `self` to its lexical parent, and a host's `self` is
      its final instance, so a nested object inherited through its host
      sees the final host; `extend Name with` updates a nested object's
      specification "preserving name and deps", ordinary `extend`
      instantiating it, `extend abstract` keeping it abstract.
    - In Blend: a nested object is folded down its host's linearization
      as a definition is. For an object O and a name N that some Q in
      L(O) introduces (`object N`, `abstract object N`) or extends
      (`extend N`, `extend abstract N`), O.N is an object of its own,
      host O: its linearization the contributors to N, from O's end of
      L(O) to the one introducing it, then the introducer's parents' own
      linearizations merged by C3; abstract as the contributor nearest
      O says. The nested objects as written become mixins, and O.N for O
      the writer's own host takes the place of today's nested object, by
      the same path.
    - A body of a contributor written in Q, copied into O.N, sees `^` as
      O.N's host chain where Q's host is in O's linearization (family
      inheritance: Outer2's Inner sees Outer2), and as its own host
      chain where it is not (`object X extends Outer.In` at the top
      level: In's `^name` is Outer's, the host it was reached through);
      a bare name falls back to the same chain.
    - Errors: `object N` where L(O) has an N already (extend it),
      `extend N` where it has none (introduce it), as `def` and `upd`.
    - Changes what nested objects are today (objects of their own,
      inherited by no one); the samples `nested` and `family-nested`
      (new) first.
    - Confirmed (the maintainer, 2026-11-04): `extend` is a mixin on the
      named object, and stays out of the top level, where it would
      change an object other modules depend on
      (`blend-namespaces-as-bends`): a top-level `extend` an error.
    - Built: objects have a kind, a top-level object (0), a nested object
      as written (1) and an extension (2), both mixins, never emitted nor
      named by path, and a nested object made for a host (3), path
      `Outer2.Inner`, its parents the host's mixins of its name down the
      host's linearization. They are made in rounds: each round finds the
      parents with the linearizations of the round before (a parent may
      name a nested object a round made), the linearizations, then the
      objects they call for, until a round makes none and moves no
      parent. A made object is abstract where its host is or its nearest
      contributor says. A contributor's body sees the host chain of the
      object it is copied into where its own host is in that chain's
      linearizations, its own past the first that is not. An extension's
      definitions are checked only in the objects made of it; a made
      object whose contributors are wrong (two introductions, or an
      extension of nothing) reports that alone. The samples
      `family-nested`, `extend-nothing`, `nested-twice`, `extend-top`;
      `nested` emits as before; tried besides: an extension within an
      extension, a nested object extending its sibling, `extend
      abstract` then an empty `extend` instantiating, nesting across an
      import with the library's datatype, `extends Outer.In` at the top
      level seeing Outer through `^`.
    - Revised the same day (`blend-frozen-host`, the maintainer: frozen
      host): a made object X.N binds its own copy of each mixin it is
      made of (an object of the mixin's kind, its host X, its members
      the mixin's, its `tpl` the mixin as written), so that a body's
      `^` is its copy's host chain, never rebound; a made object's
      parents its copies, then its introducer's parents found from X (a
      mixin has none of its own); a copy's nested mixins are its
      template's. Copies are identities of their own in C3, as the
      maintainer had it: `Z extends Outer2.Inner, Outer.Inner` errs only
      as a introduced twice, and nested objects introducing disjoint
      names inherit together. The first walk had an object reaching
      `Outer2.Inner` see Outer in Outer's bodies and Outer2 in Outer2's;
      a first fix reported a mixin bound to two hosts, a conflict where
      the real one is a name introduced twice. The samples
      `nested-reach`, `nested-diamond`.
11. `blend-object-laws` — built 2026-11-04 — laws and proofs in objects,
    sooner than first planned (the maintainer, 2026-11-04):
    - `law name:` a member stated over the object's definitions and
      types, each concrete object getting its own instance, `Obj.name`,
      bound to its own finals; a proof a definition of the same name
      (Bend pairs a law with a def of its name: `law sorted` by
      `def sorted`, in the same file or another, guide "Laws"); a law in
      an abstract object proved by each concrete one, or once for all by
      a proof the abstract object gives, updated where a family needs
      its own (`upd proof`). An unproved law stays an open claim: Bend
      prints SOME PROOFS FAIL.
    - Settled (the maintainer, 2026-11-04): a law's statement and its
      proof are kept apart, where wanted, by inheritance: laws may sit in
      an abstract root family or in a child, and proofs in another
      child, in another module given imports.
    - Built: `proof name(params):` names a law's proof, `upd proof`
      replacing one; `for` lines bind as parameters do. Blend wrote
      three files then (since one, `blend-laws-in-module`): the code, `X_LAWS.bend`
      importing it as `Blend_0`, and `X_PROOF.bend` importing both, a
      proof `def Blend_Laws.Obj.name`, as Bend's convention keeps
      `LAWS.bend` and `PROOF.bend` (the maintainer, 2026-11-04; `_`, as
      Bend imports only plain names). A proof naming a law calls its
      proof, ordered after it; code naming a law, a proof of no law and
      `upd law` are errors. scripts/check_laws.py reads `law` members in
      `.blend` files as it reads `LAWS.bend`, named by their objects
      (`Monoid.right_id`); the gate pairs each `X_LAWS.bend` with its
      `X_PROOF.bend`.
    - Revised (the maintainer, 2026-11-04): one emission writes all
      three files, or none where any has an error (`emit FILE [DIR]`,
      each path printed; no `laws` or `proof` command), and
      scripts/check_generated.sh checks them together, into results/,
      a laws or proofs file no longer written stale. An invalid
      sample's laws are no laws to check_laws.py: it is held only to its
      error. `upd law` stays forbidden, a robust foundation; theories may
      come for more (`blend-theories`). Then, from this step's open
      ends: a typed proof is a lemma, `proof add_succ(a: Nat, -b: Nat)
      -> {...}:`, in the proofs' file, named by proofs and never by code;
      `_name` in a proof, of a law that has no prior, is its proof's
      prior, written in the proofs' file with its law stated again in
      the laws' file by the prior's name, so that Bend pairs them; a
      proof's own law named in it is the proof itself, its induction,
      a prior's included, where binding late would make the prior and
      the final call each other; members know their kind, so that an
      update across kinds is an error (`upd` of a law, `upd proof` of a
      definition) and conflicts name a law as one.
    - Samples: `laws` (each family's proof by induction or cases, a
      proof once for all, `upd proof`, a lemma), `laws-imported` with
      `lib/adds.blend` (laws stated and proved in a library, a family's
      own law proved with an inherited one, a prior proof across
      modules), checked by `--verdict`; invalid `proof-no-law`,
      `law-named`, `upd-law`, `proof-twice`, `upd-proof-undefined`,
      `law-updated`, `law-shadowed`, `lemma-named`, `upd-proof-def`.
      Tried and not kept as samples: a law and proof at module level, an
      open law (SOME PROOFS FAIL in the proof file, the program still
      running).
    - Left open: a prior proof is checked against the family's finals,
      as any inherited body is, so a family that changes what a proof
      relies on proves it again (inherent, the README says so). The
      files are written one after another, not renamed into place: a
      write failing midway leaves the set mixed, which the checks
      catch.
12. `blend-typed-declares` — built 2026-11-05 — what a declared definition must
    look like (the maintainer, 2026-11-04: no way yet to say the type of
    `foo` in `declare foo`, while types may be overridden):
    - `declare def note(st: S(), +x: U32) -> S()`, a header with no
      body, `declare note(...)` sugar for it, as `upd` alone is for
      `upd def`; `declare type S: Data`, its kind optional; an untyped
      `declare after` as today.
    - The signature bound in each concrete object against its own final

    module's laws and proofs in its own file travel with its code, are

## Waypoints

matures (the maintainer, 2026-11-04): types, imports, nested objects
extended, laws and proofs in objects, typed declarations, each with its
