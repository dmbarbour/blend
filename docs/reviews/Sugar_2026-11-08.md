# Bend's sugar over Blend's objects

A review of how Bend's `do` notation and operator sugar meet Blend's
objects, 2026-11-08, from a discussion with the maintainer on type-level
objects and an object-layer `do` notation. Tried with Bend 2.0.39 and
Blend at 9cbb7e5; the scratch modules are described so that each can be
written again in a minute.

## How Bend's sugar binds

Bend's guide ("Monads"): a `do M<xs.., R>:` block desugars each
`x : A <- v` into `M.bind(xs.., A, R, v, x => ..)` and each `return e`
into `M.pure(xs.., R, e)`; the leading arguments are passed along to
both. The syntax reference: inside `(.. : T)`, `+ - * / %` call `T.add`
through `T.mod`, the bit operations and shifts their names, the
comparisons the `T.is_lt` family; without a `: T` they are refused.
Tried, 2026-11-08:

- **`M` and `T` are names, looked up literally.** Neither need be a
  type. A namespace of two defs, `Cnt.pure` and `Cnt.bind` over
  `Maybe<&2, A>` with no `Cnt` type anywhere, runs under `do Cnt<U32>:`;
  a dotted one, `Out.In`, under `do Out.In<U32>:`; a module with only
  `def Vec.add(+a: U32, +b: U32) -> U32: (a + b + 1000 : U32)` gives
  `(3 + 4 : Vec)` as 1007. The sugar is nominal: no type is inferred,
  the written name is prefixed to `bind`, `pure`, `add`.
- **A type-level def's name is not followed.** `def T() -> Data: U32`
  and `(3 + 4 : T())` fails "expected a defined name, observed T.add";
  `do M()<U32>:` is a parse error ("expected '<', observed '('"). The
  annotation wants a plain name, so a type member of Blend's, `S()`,
  can never stand in a `: S()` operator annotation or a `do` header.
  Worth an entry in glam-in-bend's `docs/BendIssues.md`.
- **`<xs.., R>`.** `R` is the block's result type: every `bind` in the
  block gets it as its `B`, each continuation being the rest of the
  block of type `M(R)`, and the final `pure` gets it as its type. `xs..`
  are whatever leading arguments the monad's `bind` and `pure` share,
  passed before the types to both: Base's `Maybe.bind(a, -A, -B, m, f)`
  and `Maybe.pure(a, -A, x)` take the quantity, so `do Maybe<&2, U32>:`;
  `Result.bind(a, b, -E, -A, -B, r, f)` takes two quantities and the
  error type, `do Result<&1, &1, String, U32>:`; `IO.bind(-A, -B, m, f)`
  takes none, `do IO<Unit>:`. A leading argument may be a term too:
  `bind(n: U32, -A, -B, m, f)` and `pure(n: U32, -A, x)` run under
  `do Tr<7, U32>:`. A bare step is a bind at `Unit`: `Some{Unit{}}` as
  a step passes, `Some{3}` is refused "expected Unit, observed U32"
  (under `do Maybe<&2, U32>:`). `x : T = v` is a plain let, no call. A
  `bind` of the wrong arity
  shows the order: with `bind(-A, m, f)`, the `R` lands in `m`'s slot
  ("expected Maybe<&2, U32>, observed Data" at the header).

## Blend today

Blend resolves every name token of a body (`rr.of`, over `TName`), a
bare name to a definition the innermost object has, else kept as
Bend's. An object's name alone is no definition, so the `M` of a `do`
header and the `T` of an operator annotation pass through as written.
A top-level concrete object with members `bind` and `pure` is therefore
already a monad for `do`, and one with `add` an operator namespace, by
accident. Tried with Blend (the module `m1`: `object Opt with shared
def pure .. shared def bind .. def both(..): do Opt<U32>: ..`, run by
`blend m1.blend`): the right answer, and `blend show m1.blend
--resolve` lists no use of `Opt.bind` or `Opt.pure` by `both`.

A monad whose carrier is a type member works end to end (`m5`: `object
Cnt with type M(-A: Type) = U32 -> (A & U32)`, `shared` `pure`, `bind`
and `tick`, `def prog() -> M(U32): do Cnt<U32>: a : U32 <- tick() ..`,
answer 2112 for a start of 10). Bend's own limits met on the way, none
Blend's: a match cannot scrutinize a computed value, so the state pair
`m(s)` is destructured in a helper `step` taking it as a parameter; a
lambda's parameter used twice wants `+s`.

## Findings

- **F1 — No late binding through the sugar.** The guide ("A first
  module"): "Each concrete object gets its own copy of every definition
  it has, its calls bound to its own final definitions". Not through a
  `do` header or an operator annotation: `m4`, `object Loud extends Opt
  with upd pure(..): None{}`, emits `Loud.both` with `do Opt<U32>:`
  still, so `Loud.both(Some{3}, Some{4})` answers 7, Opt's `pure`,
  where Loud's gives `None{}`; `object Vec2 extends Vec with upd add(..):
  (a + b + 1000 : U32)` emits `Vec2.twice` with `(a + a : Vec)`, which
  answers 6, not 1006. An update of `bind`, `pure` or an operator member
  reaches no body that uses it through the sugar. A defect against the
  guide's model, and the one that matters: the sugar over an abstract
  object (`declare bind, pure`, bodies in the abstract object writing a
  `do`) has no name to write at all today, a reference to an abstract
  object's definition being an error.
- **F2 — No callees-first order.** The guide ("What Blend writes"):
  "Callees first, as Bend requires". A use through the sugar is no
  call to Blend, so the walk does not order it: `m2`, `both` written
  above `bind` and `pure` in `Opt`, emits them in source order, and
  Bend refuses the file at `Opt.both` with "expected a filled
  definition (an unfilled law is a dead claim: live code cannot use
  it), observed Opt.bind", a message that names no cause. `m3` the
  same for `twice` above `add`. Whether a module compiles depends on
  where its members sit.
- **F3 — No use counting.** The guide ("Sharing"): "A definition is
  affine by default: used in one place ..; a second use is an error."
  `bind`, `pure` or `add` reached only through the sugar count no use:
  `m2` leaves `bind` and `pure` unmarked, affine, under two `<-` lines
  and a `return`, and Blend emits it without a word; `copied` can never be
  honored, Bend writing the one name `Opt.bind` for every bind. The
  dispositions' and sharing's laws (`sharing.copied`, `affine.emitted`)
  hold of the uses Blend reads, which these are not: the laws are
  sound, the reading is short.
- **F4 — Operators: a small surface, by the same mechanism.** Bend binds
  `+` and its kin to `T.add` and the rest of the names in Base, not to
  built-ins (the guide: "Operators, literals and brackets are sugar for
  names in Base"), so an object whose members are `add`, `mul`,
  `is_lt`.. is an operator namespace, with F1 to F3 as for `do`. The
  maintainer (2026-11-08): operators were not meant as things to
  override, and are not in glam's `.g`; leave them to Blend's future
  macro-like system (`blend-macros`). Until then, an object's name in
  an operator annotation keeps its accidental meaning, early-bound and
  uncounted, so a body of an object should annotate with a Bend type
  (`: U32`), never an object; the guide may say so.

## Outcome

- F1, F2, F3: fixed for `do` by `blend-macros.do` (merge f7beb60):
  `do self<R>:` names the concrete object, bound late, `do Obj<R>:` an
  object, bound early (`blend-do-self`); the header's object written by
  its emitted name and the uses of `bind` and `pure` as references in a
  comment ending its line, so that Blend writes them first and counts
  them; both must be `shared`. Samples `monads` and six invalid.
- F4: revised by the maintainer, operators undesigned rather than
  declined: fixed by `blend-macros.ops`, `(a + b : self)` and a nested
  object's annotation bound late, their members `shared`, an operator
  Blend does not know refused; a top-level object's name, in either
  sugar, left plain, its members' order checked.
- `alias Name`, as `.g` has it, a tentative step (`blend-macros.alias`).

## What a fix looks like

Agreed with the maintainer, 2026-11-08, for `do`; the operators left as
F4 says. The step is `blend-macros.do`, tentative, in the plan.

- **Recognize the implicit references.** A `do` header naming an object
  is a use of that object's `bind` and `pure`: Blend binds the two as
  it binds a call, records the uses so that the walk orders them before
  the body (F2), and rewrites the header's name to the concrete object's
  emitted path (F1). Only a name is rebound; Bend keeps desugaring, as
  `blend-adds-no-bend-logic` has it, and the markers stay exact: the
  same line, the same tokens but one.
- **A way to say `self`.** An object cannot name itself late today: a
  bare name is a late-bound definition, `Obj.f` early-bound, and an
  abstract object's definitions cannot be referenced. Either a name for
  the object itself, or a `do` header with no name, `do <R>:`, meaning
  the concrete object's `bind` and `pure` (the maintainer leaned to the
  nameless header, 2026-11-08). What it means in an abstract object: the
  concrete object's, so that a mixin wrapping `_bind` and `_pure` layers
  an effect over its parent's monad, each concrete object one folded
  monad, a transformer stack taken statically. The leading arguments
  stay Bend's as written, `do <&2, U32>:`.
- **Insist on `shared`.** The uses within a block cannot be counted one
  by one nor substituted one by one, Bend writing them; so a member a
  `do` reaches must be `shared`, and an affine or `copied` one is an
  error naming the member and the header's line (F3). `shared` is what
  such a member wants anyway, `bind` and `pure` having a caller at every
  step.
- **Samples first:** a valid module with a `do` over an object monad
  whose carrier is a type member, a child overriding `pure`, both
  answers printed; `bind` written below the `do` that uses it, for F2;
  invalid, a `do` over an affine `bind` and over a `copied` one; and
  the guide a section "Objects as monads" with the limit on sharing.
- **Bend's other sugar.** Each piece of Bend's name-directed sugar is a
  place Blend's reading is short: the operators (F4), and whatever Bend
  adds. Attend to each as it comes.

## Type-level objects in Bend proper

Asked beside the review: how far could Bend itself carry type-level
objects, a fixpoint of mixins at the type level?

- Types, yes. Bend's types are first-class and computable (a def
  returning `Data`, type constructors as defs, kinds), and Blend's type
  members are exactly that: an object's associated types live at Bend's
  type level, erased, and a typed declaration's witness is Bend checking
  a signature over them.
- Methods, no. A record of methods is `Type`-kinded (a closure is never
  `Data`), so affine: one call consumes the dictionary. Open recursion, a
  `self` passed to a mixin and the knot tied by a fixpoint, needs a
  general fixpoint Bend's termination check refuses, and Bend has no
  mutual recursion between defs; even an `@unsafe` knot makes every
  method call indirect, which defeats the single-caller folding that is
  the README's reason for Blend. A template cannot tie the knot: a
  `~self` must be closed and a template calls only templates declared
  above it, so the fixpoint must already exist as a named def before the
  template is applied. That def, per concrete object, is what Blend
  emits.
- So the signature lives at Bend's type level and the method fixpoint is
  taken before Bend sees the program, in Blend. Nothing in Bend
  dispatches on types, which is what makes an object-layer `do` cheap:
  a name is all the sugar wants.
